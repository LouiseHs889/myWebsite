N+1 問題

甚麼是 N+1 問題?

原本預期只用一條 SQL 撈資料，執行時卻發現實際發出的 SQL 多了好幾倍，導致載入資料非常耗時。

N+1 指的是：1 條查主表的 SQL，加上 N 條查關聯資料的 SQL。其中 N 是主表查詢回傳的筆數。如果主表有多個 lazy 關聯被存取，數量還會倍增。以下面的範例來說，查出 N 筆 Diagram 會產生 1 + 2N 條 SQL。

怎麼發生的?

使用 JPA 查詢時，如果 Entity 中有 @OneToMany（或其他關聯）且 FetchType 為 LAZY，關聯資料不會跟著主表一起載入，而是在第一次被存取時才另外發 SQL。

如果在 DTO 的建構子中逐筆存取這些 lazy 集合，每一筆主表資料都會各自觸發查詢，就形成了 N+1。

解決方法的選擇:

Join Fetch:
一次把關聯資料 join 進來。但它不能搭配 select new Dto(entity) 這類 constructor expression，同時 fetch 多個 List 集合會拋出 MultipleBagFetchException，搭配分頁也有問題。能不能用，取決於 Entity 和查詢原本的寫法。

Batch Fetching:

保留 lazy 特性，但把 N 次查詢合併成少數幾次 IN 查詢，屬於侵入性較低的做法。

最終我自己的選擇:

主表 Entity 中有多個 @OneToMany + LAZY 的欄位，而 DTO 的建構子會直接逐筆讀取這些關聯集合並轉成 List，因此造成 N+1。我嘗試過 Join Fetch 和 Batch Fetching，但在這個情境下都無法順利套用。再加上原本的建構子在很多地方都有被使用，不適合直接修改，所以最後採用以下做法：

  1. 在 DTO 另外寫一個建構子，只接收主表欄位，one-to-many 的欄位先初始化成空的 List。
  2. 先用一條 SQL 查出主表中符合條件的資料。
  3. 收集這些資料的 id，用 IN 查詢一次撈出所有對應的子表資料（group、role 各一條）。
  4. 將子表資料依 diagram_id 分組，填回對應的 DTO。

這樣不論主表有幾筆，SQL 數量都固定為 1 + 關聯表數量（此例為 3 條）。

成效：主表約 82 筆，執行時間從 27,640 ms 降到 465 ms，約快了 59 倍。
